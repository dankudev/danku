# danku

## Development

### Cloudflare API client

`packages/danku/src/resources/cloudflare/generated/` holds `CloudflareClient`, a typed client for only the Cloudflare endpoints danku calls, generated by [Kubb](https://kubb.dev) from Cloudflare's OpenAPI spec. It is committed, so building and testing never need the network. To call a new endpoint, add its operationId (from Cloudflare's API docs) to `include` in `packages/danku/kubb.config.ts`, then regenerate from `packages/danku`:

```bash
vp run openapi
```

Kubb prints a telemetry notice at startup; the config sets `KUBB_DISABLE_TELEMETRY`, so nothing is sent.

### Testing `danku deploy` against real Cloudflare

The test suite only talks to a fake Cloudflare. To try a real deploy, create a throwaway project outside this repo and link the local danku into it. Use a Cloudflare account you can experiment in: this creates real resources.

**1. Build the CLI** (from the repo root):

```bash
vp run -r build
```

**2. Create a test project** next to this repo, e.g. in `S:\Programming`. It needs `vp` and `pnpm` installed, like any `danku create` run, and refuses to run inside this repo.

```bash
node DANKU/danku/packages/danku/bin/danku.mjs create danku-test saas
cd danku-test
```

The root `package.json` `name` becomes the project name in every cloud name (`danku-test-db`), so it must be lowercase letters, digits and dashes.

**3. Install the local danku** as a link, so rebuilding it (`vp pack` in `packages/danku`) is enough to pick up changes:

```bash
vp add -D -w link:../DANKU/danku/packages/danku
```

**4. Declare a database** in `danku/deploy.ts` at the test project's root:

```ts
import { D1 } from "@dankudev/danku/deploy/cloudflare";

new D1("db");
```

**5. Create a Cloudflare account API token.** Use an **account** token, not a personal one from My Profile: it belongs to the account rather than to you, so CI keeps working if your membership changes, and Cloudflare's tagging docs recommend it for automation. In the dashboard, open the test account → **Manage Account** → **Account API Tokens** → **Create Token** → **Create Custom Token**:

A policy with **Entire Account** as its resources (account-level permissions):

- **Developer Platform → D1 → Edit** (the API calls this group "D1 Write"; Edit includes reading): `danku deploy` creates databases.
- **Workers → Admin**: wrangler uploads Workers. Editor isn't enough: it can't create new Workers. The legacy **Workers Scripts → Edit** still works, but Admin is its replacement.
- **App Security → Tag Management → Edit**: danku finds and labels its resources through tags. Search for "tag" to find it. Don't confuse it with **Access: Tags**, which is for Zero Trust Access.

For a `Zone` (a Worker served on your domain), domain permissions appear under **All Domains** (or one domain) and need a second policy. Not yet confirmed against a real account: **Zone → Zone → Read** (danku lists zones), plus whatever Cloudflare asks for when wrangler attaches the custom domain (likely **Zone → Workers Routes → Edit**) and when danku tags the zone.

**Tagging may not work on every account yet.** The changelog says Resource Tagging is in public beta and rolling out to all accounts (2026-04-27), but Cloudflare's OpenAPI spec marks the tag endpoints as Enterprise-only and lists only the Global API Key for them. The second `curl` below tells you which is true for your account: a 403 saying "Tagging is not enabled for this account" means the account doesn't have it, and danku can't deploy there until that changes.

The **account ID** is on the account's home page in the dashboard (right-hand side, "Account ID"), and in the dashboard URL: `dash.cloudflare.com/<account id>`.

Check the token before deploying. Both calls should answer `"success": true`:

```bash
curl https://api.cloudflare.com/client/v4/accounts/<account id>/d1/database -H "Authorization: Bearer <token>"
curl https://api.cloudflare.com/client/v4/accounts/<account id>/tags/keys -H "Authorization: Bearer <token>"
```

**6. Deploy.** `CI=true` makes this a production deploy; without it, D1 is skipped as a dev-only run. In PowerShell:

```powershell
$env:CLOUDFLARE_API_TOKEN = "<token>"
$env:CLOUDFLARE_ACCOUNT_ID = "<account id>"
$env:CI = "true"
vpx danku deploy
```

What to expect:

| Run                           | Output                                                                                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| First deploy                  | `+ D1 db: create danku-test-db`; the database appears under **Storage & Databases → D1**, and its `danku.*` tags under **Manage Account → Resource Tagging** |
| Again, unchanged              | `= D1 db: no changes`, and nothing is written                                                                                                                |
| After renaming `db` to `main` | `+ D1 main: create danku-test-main` and `! D1 db: danku-test-db is no longer in danku/deploy.ts; …` (the old database is kept)                               |
| Without `$env:CI`             | `· D1 db: skipped in dev`, no Cloudflare calls                                                                                                               |

**7. Clean up.** danku never deletes databases, so delete them yourself, e.g. `vpx wrangler d1 delete danku-test-db` from `apps/web`, or in the dashboard. Close the terminal (or `Remove-Item Env:CI, Env:CLOUDFLARE_API_TOKEN, Env:CLOUDFLARE_ACCOUNT_ID`) so later commands don't run as production.
